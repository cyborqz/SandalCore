# mapc: the area's ground, offline

`mapc` reads the game's cooked map and builds what worldd stands and walks its NPCs on (plan E1, stage 2; an uncommitted draft). It is a .NET 8 console
project next to `contentc`'s Go one: it runs when the game's files or the area change, never at worldd's start.

```
dotnet build -c Release tools/mapc                       # (needs third_party/CUE4Parse: powershell -File tools\mapc\fetch_cue4parse.ps1)
dotnet tools/mapc/bin/Release/net8.0/mapc.dll build      # the three files below, into dist/content
dotnet tools/mapc/bin/Release/net8.0/mapc.dll --check    # rebuild all three in a scratch folder and compare them byte for byte with dist/content's
```

Run it from the repository root. It needs `dist\Release\aoc_navbuild.exe` (`scripts\build.ps1 -Target aoc_navbuild`: the Recast half, below), the
game's `Content\Paks` (read only: `<AOC_CLIENT_DIR>\AOC\Content\Paks` (default: `%GAME_ROOT%\AOC\Content\Paks`), `--paks`) and `dist\content\aoc.usmap`
(`--usmap`). `mapc npc-motion` writes only the Blueprints' table (about a minute, 4 GB; `build` and `--check` do it first and give its memory back). **Memory:** the map read (`extract`, and so `build` and `--check`) reads the cells one at a time (the E1 review's I3): a cell's package, its exports and the static-mesh packages its imports resolved to are let go before the next cell is read (CUE4Parse's provider keeps no package cache: every `LoadPackage` parses anew), so the heap holds one cell and the collision shapes of the meshes seen so far (`MeshGeo`) instead of all 232 cells. Before that the whole read kept 45 M triangles and peaked above 14 GB (it was stopped by a 14.5 GB heap limit, and by a guard at 0.6 GB free of 31 GB with a game running). Still run it with the machine otherwise idle: the Blueprint pass is 4 GB, the navmesh build runs on every core. The output does not depend on the order the cells are read in (the placements are sorted, the meshes numbered by first use): `--check` holds it. `mapc extract` writes only the geometry; `mapc probe KEY.tsv` and `mapc inspect NAME...` are diagnostics.

| Output | What | Size |
|---|---|---|
| `dist/content/area_geom.bin` | the area's geometry: the landscape's heightfield and the placed pawn-blocking meshes (format in `GeomFile.cs`) | 40.8 MB |
| `dist/content/area_nav.bin` | the terrain (the client's own 16-bit height samples) and the tiled Detour navmesh (format in `server/worldd/nav/nav_file.h`) | 85.1 MB |
| `dist/content/npc_motion.tsv` | every pawn Blueprint's facts (`NpcBlueprints.cs`, one line per class that descends from `NPCPawn_C`, 2,169 of them): its parents, `DefaultScale`, `StartingAlignments`, capsule half height and radius, `CharacterMovement`'s speeds, rotation rate and default movement mode, flying speed, tags | 561 KB |

**Mounts** (the mounts milestone, stage 1): `mapc mount-speeds` reads only the 141 packages of `GameBlueprints/Mounts` (no map, a few seconds) and writes `dist/content/mount_speeds.tsv`: one line per Blueprint with a class default object, `blueprint kind parents max_walk_speed max_run_speed max_fly_speed max_swim_speed defaults` (the movement component's four speeds along the Blueprint's parents: a child keeps the defaults of `Mount_Grounded_Base`, `Mount_Flying_Base`, `Mount_Aquatic_Base` and `Mount_Base` and sets what it changes; `defaults` names a speed no Blueprint of the chain sets, which then reads the engine's default 600 for walk and fly, 300 for swim, the walk speed for run). **A ground mount's speed is its `MaxRunSpeed`** (990 for the 165 % terror bird, the number capture 959 measures; the walk speed is 220 in every Blueprint but two), a flyer's `MaxFlySpeed` (1,290 for 215 %), an aquatic mount's `MaxSwimSpeed` (920 for 230 %). `mapc mount-speeds --check` writes nothing and exits 1 when `dist/content/mount_speeds.tsv` differs from a fresh read. **The rider AnimBPs** (stage 3 fix 2): the same pass writes `dist/content/mount_riders.tsv` (`blueprint rider_anim`): the class path of the AnimBP each Blueprint's `InteractableComponent` interaction point (`Mount_Interaction`) names as `AttachmentAnimation`, along the Blueprint's parents (137 of 140 Blueprints name one; the terror bird's is `ABP_PC_MNT_Swiftclaw_C`, the Shoalskipper's `ABP_PC_MNT_Tidesnapper_C`, the Dawnbreaker's `ABP_PC_MNT_Dawnbreaker_C`, the AnimBPs retail's opens export). worldd names it in a mount's interaction data and exports it with the open, which is what puts the rider's mesh on the riding pose. `--check` compares both files. The speeds are the mount's own at MoveSpeedMult 1 (the server multiplies them: roads +0.10 to +0.30, the dash x1.35); the item texts' percentages are the same numbers over the base (165 % ground speed is 990 = 600 x 1.65, 215 % flying speed 1,290, an aquatic mount's 230 % water speed 920 = 400 x 2.30), and `services/cmd/contentc`'s real test holds the two to each other: 140 Blueprints, every item's Blueprint has its speeds, the text and the Blueprint agree for all but five items (the two GM Eagle Gryphons, which share one Blueprint: their text says 165 % and 215 % but that Blueprint, a plain child of `Mount_Flying_Base`, runs 600 and flies 800; the Alligator shares the crocodile's Blueprint, the Corrales Fox and the Glimmering Geode differ from their text), and the 22 ground items whose text names no speed have their Blueprint's. **The Blueprint is the speed**: the client simulates with it.

**The profession level-up curves** (Gathering stage 2, "Gathering data"): `mapc artisan-curves` reads the three pak assets `/Game/DesignAssets/Artisanship/{Gathering,Processing,Crafting}/...LevelUpCurve` (a `CurveFloat` each; no map, a second) and writes `dist/content/artisan_curves.tsv`, one line per key: `curve ord time value interp arrive_tangent leave_tangent pre_extrap post_extrap` (`curve` is the package path a `LevelUpCurve`'s `ExternalCurve` names before the dot; time is the profession level, value the XP total of that level; floats are the asset's float32, written round-trip). The design database has none of it: the 22 profession leveling types keep a placeholder (0 XP at level 0, 50,000 at level 50) and the three `StatCurve`s have no keys, because Unreal uses the external curve when one is set. The three assets are identical: 50 keys, `Linear`, level 1 at 5.1922868E-08 XP and `400 x level^2` XP from level 2 (1,600) to level 50 (1,000,000). `services/cmd/contentc` reads the file (`--artisan-curves`, default `dist/content/artisan_curves.tsv`) into `stat_curve` and `leveling_curve`. `mapc artisan-curves --check` writes nothing and exits 1 when the file differs from a fresh read. It is a pak read, not a map read, but it is a heavy-lock job like every mapc run.

**Roads** (the mounts milestone, stage 4): `mapc roads` reads the road splines of the MainGrid cells around the area (the area's circle plus the geometry margin: 122 cells, one at a time) into `dist/content/roads_raw.tsv`. It is a MAP READ: run it alone (no build, no game, no other heavy job). Only `BP_RoadActor_C` and its `IntrepidSplineComponent` are deserialized: the cell's export map is filtered by name and by outer index (`Roads.cs`), the rest of the cell is never parsed, and the cell is let go before the next. The actor's `RoadPreset` and `OwnerZOI` (64-bit record guids) and the spline's `SplineCurves.Position.Points` (OutVal, ArriveTangent, LeaveTangent: a cubic Hermite per segment) with the component's world transform are sampled every 200 cm into XY polylines; a road that appears in two cells is kept once. One line per road: `road <TAB> preset_guid <TAB> zoi_guid <TAB> active <TAB> in_node <TAB> cell <TAB> actor <TAB> x,y ...`. Measured on E1's area: 121 cells read (1 named by the map and not in the containers), 31 hold road actors, 49 actors, all 49 decoded (the earlier hand decode had 45), 18.3 km, 9,584 samples, **11 s and a 2.7 GB peak working set**; 41 of the hand decode's 45 polylines match within 94 cm (median 2). `mapc roads --check` writes nothing and exits 1 when the file differs from a fresh read; `mapc roads --probe CELLID` shows what one cell's road actors hold. `contentc roads` (`services/README.md`) resolves each road's tier and width and writes `dist/content/roads.tsv`, which worldd loads.

`npc_motion.tsv` has four columns the stage 3 filter and combat read (`NpcBlueprints.cs`): `placeholder` and `hidden` with the `mesh` and `anim` the Blueprint's CharacterMesh0 resolves to (a humanoid's body is merged at run time from its NPCAppearance; the spawn filter leaves such a Blueprint out), and the combat facts `lists` (the three stat initializer lists, "base;list1;list2" as record guids), `dist` (the eight StatDistribution weights), `elite` (the EliteLevelRanks "level:rank,...") and `rewards` (the RewardTable guids of its Rewards, part 2 reads them).

The outputs are the same bytes every run (the placements are sorted by mesh and place, the navmesh tiles are built by a thread pool and written in tile order);
`--check` is the gate. It means the same wherever it stands on the line (the mounts review, B I2): alone or with `build` or `extract` it is the full check above (14 GB, run alone), `mapc mount-speeds --check`, `mapc artisan-curves --check` and `mapc roads --check` (also written `mapc --check roads`) compare their own files only, and anything else is refused; `mapc --explain ARGS` prints how a line is read and does no work.

## The Riverlands (G1, stage 1; an uncommitted draft)

The world is the whole Riverlands now: the 12 ZOIs whose biome is Riverlands, 49.12 km2, as the exact 401 rectangles of `tools/mapc/region_rects.tsv` (written by `python tools/capture/gen_region.py` from `fixtures/region/*.json`, which `tools/capture/gen_region_rects.py` cuts from the game's zone-of-influence grid; `gen_region.py` also writes worldd's `spawns/region_data.h`; `extract_game_data.bat` runs both). **A region is mapc's default; `--center X,Y --radius CM` is E1's circle (review B I7: it needs its own `--out-dir`, because the default `dist/content` holds the Riverlands' files, and it has no `--check`: E1's files were made by an earlier mapc, geometry version 1, mesh names without `@hash`, and 7 of its tiles differ since the package-path fix, so they cannot be reproduced byte for byte; E1's guarantee is `test_worldd_nav_window`'s comparison of its tiles with the region's, below)** (`--region FILE` names another set of rectangles; `--margin` is the geometry margin, 150 m, for the rectangles as for the circle).

```
mapc probe-cells [--batches M]                master umap only (4 s): the cells the region reads, per grid, their packages' sizes and how M batches would cut them
mapc extract [--batches M] [--heap-gb G]      the map read as M child processes (default 12) -> area_geom.bin + region_foliage.tsv
mapc build / mapc --check                     extract, aoc_navbuild (the chunked area_nav.bin), the Blueprints; --check rebuilds in a scratch folder and compares
mapc roads [--check]                          the road splines of the region's MainGrid cells -> roads_raw.tsv, then `contentc roads`
```

**What the region reads** (`probe-cells`): 3,170 cells touch the footprint plus its margin; 1,636 are read: MainGrid 799, Foliage 711, Landscape 78, Water 48 (3.3 GB of packages; the HLOD grids' 1,534 proxy cells are not read; 3 cells are named by the map and are in no container). The estimate of the research (1,735) was for the 516 chunks that bound the footprint.

**Batches.** `extract` cuts the read set into `--batches M` runs of about equal package size, in bands of 256 m from the south (every batch is a strip of the map with all four grids in it: `Cells.Split`, a function of the cell list alone) and runs them as child processes **one at a time**: each under `DOTNET_GCHeapHardLimit` (`--heap-gb`, 8 by default; non-concurrent GC) and behind a guard that waits (`--wait-minutes`, 40) until at least `--min-free-gb` (6) of memory is free and **no game client (`AOCClient*`), build (`MSBuild`, `cl`, `link`, `cmake`) or `aoc_navbuild` runs**. A child reads its slice cell by cell (a cell's package, its exports and the meshes' packages are let go before the next), writes a part (the geometry file's own format, a `.src` sidecar and its foliage rows) into `<out-dir>/mapc_batches/`, and the parent merges the parts (`GeomFile.Merge`). A finished part is reused by the next run if the batches' signature (the cut, the region, mapc.dll, and the write times of the paks directory and the usmap: a game patch between a crash and the re-run must not mix old parts with new) is the same **and its three files still have the length and the FNV-1a 64 that the `.done` marker recorded** (review B I5: the marker is written last, whole, by a temporary renamed over it, after the part, its `.src` and its foliage rows were read back and flushed to the disk; NTFS can keep a file's length with zeroed data after a power cut), so a crash or a reset loses one batch, not the read; the parts are deleted after a successful merge (`--keep-parts`). `--stop-after N` runs batches 0..N and prints their time and peak memory without merging (the measurement run); `--cells N/M --part FILE` is the child's own command line.
- **Measured (the first batch alone, then all 12):** batch 0 (274 cells, 260 MB of packages) 31 s and a **3.34 GB peak working set**; all 12 batches 212 to 243 s in all (8 to 36 s each), **the largest peak 3.8 GB**, the smallest 2.3 GB; the merge takes a second or two and writing the files about ten. The Blueprint pass of `build` (1 min, 4 GB) runs first, in this process, and gives its memory back.
- **The result does not depend on the cut or the order.** The placements are sorted by mesh name and place; the meshes are numbered by first use of the sorted placements; of two placements that are one (same mesh, same place and rotation: a component two packages hold) the one of the **lowest source rank** wins (0 the persistent level, then the cells sorted by name: the one E1's single-process read met first), so E1's choice is kept whichever batch reads it.
- **Three findings of the first region reads, all fixed** (each would have broken the navmesh or E1's tiles): (1) the BodySetup of `ConstructionPiece_HuAela_Mod_Bridge_Segment_1` holds a box of 2,097,150 x 2,097,153 x 6,809 cm (a default; the mesh is 20 m across): placed five times east of Aela it made every navmesh tile within 10 km see a wall and come out as one polygon. A simple shape larger than 1 km in a direction (`MeshShapes.MaxShapeCm`) is left out (3 meshes, counted as `meshes.hugeShapesSkipped`). (2) **19 pairs of assets share a short name** (`Aela_Rubble_Block_Curb01` in two packages, `SM_AelanStoneBench_01_damage_01` with two different shapes ...): E1's read, which keyed a mesh by its short name, merged each pair into one mesh. A mesh is now keyed by its package path and named `<short name>@<hash of the path>` in the file (the hash after the closing quote: the order of different short names, which sorts the placements, is E1's). Seven of E1's tiles change with it (below). (3) The duplicates rule above.

**Foliage, in the same pass (stage 3's input).** `IntrepidGatherableFISMC_*` components of the Foliage cells are `UFoliageInstancedStaticMeshComponent`s to CUE4Parse (it walks up the usmap's super classes): `DDERecordName` (e.g. `Tree_Oak_Large_2`) and `DDERecordId` name the def (**a `GatheringFoliageData` record of the design data, not a GatherableActorDef**: 68 of the 73 ids are GatheringFoliageData guids in content.db, none is a GatherableActorDef's), `GatherableGameplayTagMap` maps an instance index to tags (`NearWater`, `Highlands`, `Cave`, ...), the instances are the component's `PerInstanceSMData` under the component's transform. `dist/content/region_foliage.tsv` (version 2) holds one line per instance inside the footprint (no margin): `def_id def_name cell owner component index x y z yaw pitch roll sx sy sz mesh tags` (world cm and degrees; `index` = the instance's place in the component's `PerInstanceSMData`, which is what the cell's `AIntrepidStateIFA` indexes by; the cell is its package's name; **the instance's key is (cell, owner, component, index)**: a component's name, `IntrepidGatherableFISMC_0` ..., repeats across the actors of a cell, and the first version's key (cell, component, index) was shared by 565 pairs of instances in 33 cells; `owner` is the `InstancedFoliageActor_...` that holds the component, and the key is unique now). **84,218 instances of 73 defs, 19.3 MB. 3,535 instances (4.2 %, 13 names: six Ash trees, `Tree_Oak_Medium_2` and `_3`, `Tree_Oak_Medium_FTUE` and four Riverlands rock pillars) have `def_id` 0: the component names its def and does not serialize the id (the archetype chain does not hold it either); each of the 13 names is the name of exactly one `GatheringFoliageData` record in content.db, so the reader resolves a 0 by `def_name`.** A name can also carry two ids in the file (`Tree_Oak_Large_3`: three; the 109... ids are older records). Checked against the heightfield, the instances stand on it within 15 cm (median 0) in every ZOI.

**Roads.** `mapc roads` takes the region's 799 MainGrid cells (798 read, 9 s, 2.8 GB peak working set): 145 road actors (E1's circle held 49), 53.9 km, 28,087 samples; `contentc roads` keeps 91 at Wilderness (Riverlands Artery T1 54 roads 24.7 km, Lions Hold T2 37 roads 9.1 km; 54 give a mount nothing: Veins, Capillaries, `Node_N3`). worldd loads `roads.tsv` as before.

The navmesh: **the tiles are 4,000 cm and anchored on E1's corner (the login spot - 112,000 cm), so that E1's tiles are the same tiles**; a tile is built when it touches a rectangle (the footprint, no margin: nothing is walkable beyond the edge); chunk (cx, cy) = (floor(tx / 8), floor(ty / 8)), tile indices reach into the negative. aoc_navbuild takes `--threads` (mapc passes half the machine's by default; the bytes do not depend on it): 123 to 177 s on 8 threads, 1.2 GB peak. The largest tile has 1,020 polygons (Detour's limit is 1,024: 8 tiles needed a coarser simplification to fit, deterministically; E1's largest had 800). `aoc_navbuild --info FILE [--verify]` prints a file's numbers and reads every chunk back; `--compare A B` is what `--check` uses.

**E1's tiles.** Of E1's 2,488 tiles, 263 lie outside the Riverlands (the circle reaches past the footprint) and are not built; of the 2,225 in both, **2,216 are byte for byte the same**. The 9 that differ are all explained: 7 stand near the `SM_AelanStoneBench_*` assets that share a short name with another asset (E1's read had merged them), 2 are on E1's rim (1.1 km out) where E1's circle cut placements the region keeps. `test_worldd_nav_window` checks this against `dist/content/e1/area_nav.bin` (E1's own file, kept there; `AOC_E1_NAV`).

**What worldd does with these files (G1 stage 1, Part B).** `area_nav.bin` is streamed in a window of at most 4,096 tiles (`server/worldd/README.md`, "The chunked ground"); the load test with the whole population and six players crossing the region at 22 m/s for 15 simulated minutes peaked at exactly that cap with no chunk failing, a pump of the window costing the world tick 4.0 ms at most and the world tick 4.6 ms at most. `npc_motion.tsv` is unchanged and decides which Blueprints can be spawned. `region_foliage.tsv` (84,218 gatherable instances, 73 defs) is stage 3's input and is not read by worldd yet. **Node positions do not come from mapc**: the design data has none, and the painted foliage is stage 3's; the 439 nodes worldd places are the ones retail's captures saw (`tools/capture/find_region_nodes.py`, `fixtures/region/node_picks.json`). The ground has one known gap that matters to the GM garden and the node towns: in Joeva and Winstead the live towns stand 40 to 57 m above the cooked heightfield (Part A's region answer key), so a node placed on the extracted ground there would sit under the town; the garden is at the login spot, in Ruins of Aela, where the key agrees with the ground.

**`mapc --check`** (alone, the machine idle: the Blueprint pass, the 12 batches, the navmesh) rebuilds `area_geom.bin`, `area_nav.bin`, `npc_motion.tsv` and `region_foliage.tsv` in a scratch folder and compares them with `dist/content`'s: the geometry, the table and the foliage byte for byte, the navmesh **by chunk** (the header, the region, the terrain grids' hashes and each chunk's tile count, size and hash; it names the chunks that differ). It does not rebuild the roads: `mapc roads --check`. (The chunk and region hashes are FNV-1a 64 with E1's offset basis 1469598103934665603, a digit short of the standard 14695981039346656037: consistent everywhere, but a standard FNV tool cannot reproduce them.)

## From a clean checkout

`dist/` is git-ignored: the ground, the navmesh, the Blueprint table and `content.db` are built, not committed. `extract_game_data.bat` (`scripts\extract_game_data.ps1`) builds all of it from your own game install, in this order, and skips what is up to date:

1. `powershell -File tools\mapc\fetch_cue4parse.ps1` (the pinned CUE4Parse commit under `third_party/CUE4Parse`), `dotnet build -c Release tools/mapc`, and contentc (Go);
2. `mapc export-config` (the game's `AOC/Config` files, as the game ships them, into `dist/content/client_config`) and the mappings file `layouts\aoc.usmap` copied to `dist\content`; `mapc artisan-curves` and `mapc mount-speeds`;
3. `contentc`: `content.db`;
4. `mapc export-zoi` (the layer 0 chunks of the zone-of-influence grid into `dist/content/zoi_chunks`), `tools/capture/gen_region_rects.py` and `gen_region.py` (the Riverlands' rectangles, `tools/mapc/region_rects.tsv`), and the generators of the sources the build includes;
5. `scripts\build.ps1 -Target aoc_navbuild` (the Recast half: `dist\Release\aoc_navbuild.exe`);
6. `mapc roads`, then `contentc roads` and `contentc roads --levels`;
7. `dotnet tools/mapc/bin/Release/net8.0/mapc.dll build` with the game's `Content\Paks` and `dist\content\aoc.usmap`: `area_geom.bin`, `area_nav.bin`, `npc_motion.tsv`, `region_foliage.tsv` (the machine otherwise idle).

Without `npc_motion.tsv` worldd makes no generic NPC (`NoTable`) and the spawn filter's visuals verdicts are off (the invisible villagers return); without
`area_nav.bin` there is no ground: the NPCs stand where stage 1 put them AND worldd never starts its combat system, so every mob
shows 0 HP and damage does nothing (worldd starts combat only after the navmesh loads).

## What it reads and how

**The containers.** CUE4Parse reads the game's `.utoc/.ucas` and `.pak` files (180 of 181 mount; `global.utoc` is only the script-object store): they are not
encrypted (the all-zero key mounts them), the engine is UE 5.6 (`GAME_UE5_6`: 5.5 reads a zen package header wrongly), compression is not used by the files
read. The exported loose files in `<AOC_EXPORT_DIR>` are zen packages without the container header and the global script-object store a zen package's
imports need, which CUE4Parse's loose-file provider does not have: the containers are the source. `dist/content/aoc.usmap` is version 4 (explicit enum
values) and CUE4Parse of the pinned commit reads up to version 3: `UsmapCompat.cs` rewrites it in memory.

**The map.** `Verra_World_Master.umap` is the World Partition level: 16,026 streaming cells with their content bounds; 497 cells touch the area (1 km and 150 m
of margin); the `MainGrid` (static meshes and Blueprint actors), `Foliage`, `Landscape` and `Water` grids are read (121, 89, 12 and 10 cells), the HLOD
grids (`Main0`, `Foliage1` ...: visual proxies, 235 cells) are not; two cells (a `MainGrid` and a `Water` one) are in no container of the game. The persistent level's
own static meshes are read too. 176,182 mesh components were seen; 101,431 placements of 1,135 meshes are within reach of the area (45.4 M triangles).

**The ground.** A landscape component is a heightmap texture of 16-bit samples in the UE 5.5 landscape storage format (delta coded, decoded by CUE4Parse's
`ULandscapeTextureStorageProviderFactory`): 48 components of 511 x 511 vertices at 100 cm, the 16-bit value times 150/128 cm above the actor's height. The
heights are used as they are (the quad's diagonal as UE splits it): every captured player's ground lies on them to 1 cm.

**The collision of a placed mesh.** What stops a walking pawn, as UE's character movement sweeps: the component's collision profile blocks the Pawn channel
(the profile table is the game's `DefaultEngine.ini`; a blueprint component's profile comes from its parents, field by field; a component that says "Default" uses the
mesh's `BodySetup` default) and the mesh has a shape: its **simple** shapes (boxes, spheres, capsules and convex hulls of `BodySetup.AggGeom`), or, when its
trace flag is `UseComplexAsSimple` (83 meshes: rocks and cliffs), the render LOD the collision is built from as triangles. Instances (`InstancedStaticMeshComponent`,
the foliage's) are placed by their transforms. 7,813 components have no shape, 1,689 a non-blocking profile (the volumetric fog's cubes among them).

**The navmesh** (`aoc_navbuild`, `server/worldd/nav/nav_build.cpp`; Recast and Detour v1.6.0 in `third_party/recastnavigation`): the settings are the game's own where
`DefaultEngine.ini` says (the navigation system's Default agent radius 35 and height 144, slope 52, 4,000 cm tiles, watershed regions); cells of 25 x 10 cm (the game's
resolutions are 40/20/10 wide by 20 high), a climb of 45 cm (UE's `MaxStepHeight` and the move checker's ledge; the game's navmesh says 100). 2,488 tiles of the 2.2 km square
(a tile with no ground is left out), 330,849 polygons, built in about 5 s on all cores.

## What is modelled and what is not

- **Not read:** spline meshes (9,198 components: roads and the like), the water (the rivers' beds count as ground), the landscape's visibility layer (holes: caves),
  the HLOD levels, Blueprint actors whose class does not load (a few: the collision of what they bring is lost), movable or destroyable parts, the doors (an
  open doorway is walkable, a closed door is not drawn here at all), the BSP brushes.
- **Modelled:** a pawn's capsule is the navmesh's agent (radius 35, height 144), whatever its archetype; the climb of 45 cm.
- The extraction's measure is the captured ground (`tools/capture/gen_ground_key.py`, `server/worldd/tests/test_worldd_nav.cpp`): 334 of 335 captured ground
  positions (players' ServerMovePacked and the NPCs' and other players' ReplicatedMovement, within 1.1 km of the login spot) lie on the heightfield or a floor of the
  navmesh, the 245 positions of walking players are all on the navmesh within 80 cm, and a path joins every pair of walked places; the one miss is a creature 787 cm under the terrain (a cave).

  (`mapc.csproj`) with the NuGet packages its project names (Blake3, BouncyCastle, FixedMathSharp, Fmod5Sharp, GenericReader, Infrablack.UE4Config,
  K4os.Compression.LZ4.Streams, LZMA-SDK, Newtonsoft.Json, OffiUtils 3.0.0, Oodle.NET, Serilog, VGAudio, Zlib-ng.NET, ZstdSharp.Port). The NuGet package of the right
  version (1.2.2) cannot read the game's container headers (version 5) and the newer ones need .NET 10. Nothing is decompressed with Oodle and no Oodle library is
  fetched. `fetch_cue4parse.ps1` fetches the folder (it is in `.gitignore`).
- **Recast and Detour** (zlib, `github.com/recastnavigation/recastnavigation`), v1.6.0 (`6dc1667f`), `Recast/` and `Detour/` only, 689 KB, unmodified, in
  `third_party/recastnavigation` (committed); `server/worldd/CMakeLists.txt` builds them as `recast_detour`.
